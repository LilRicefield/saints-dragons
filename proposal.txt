🔍 Analysis: Current Spawn System

  I have significant duplication:

  Fabric: 340 lines
  Forge: 210 lines
  Duplication: ~80% of logic is identical between platforms

  Current Problems:
  1. ❌ Each dragon hardcoded in both platform files (5-7 lines each)
  2. ❌ Biome tags duplicated across platforms
  3. ❌ Adding a new dragon = edit 3 files (Fabric, Forge, Config)
  4. ❌ Platform code has intimate knowledge of all dragons
  5. ❌ Helper methods duplicated (normalizeBiomeId, normalizeBiomeTag, etc.)

  ---
  ✅ Recommended Architecture: Central Spawn Registry

  Principle: Data-Driven Registration

  Platform code should be generic. Dragon-specific data should live in common.

  ---
  📐 Proposed Design

  1. Create Common Spawn Data (common/src/.../world/DragonSpawnRegistry.java)

  package com.leon.saintsdragons.common.world;

  public final class DragonSpawnRegistry {
      private static final List<DragonSpawnEntry> ENTRIES = new ArrayList<>();

      public static void register() {
          // Register all dragon spawns
          add(ModEntities.RAEVYX, "has_raevyx",
              () -> SaintsDragonsConfig.RAEVYX_SPAWN_WEIGHT.get(),
              () -> SaintsDragonsConfig.RAEVYX_MIN_GROUP_SIZE.get(),
              () -> SaintsDragonsConfig.RAEVYX_MAX_GROUP_SIZE.get(),
              SaintsDragonsConfig.RAEVYX_ADDITIONAL_BIOMES,
              SaintsDragonsConfig.RAEVYX_EXCLUDED_BIOMES);

          add(ModEntities.IGNIVORUS, "has_ignivorus",
              () -> SaintsDragonsConfig.IGNIVORUS_SPAWN_WEIGHT.get(),
              () -> SaintsDragonsConfig.IGNIVORUS_MIN_GROUP_SIZE.get(),
              () -> SaintsDragonsConfig.IGNIVORUS_MAX_GROUP_SIZE.get(),
              SaintsDragonsConfig.IGNIVORUS_ADDITIONAL_BIOMES,
              SaintsDragonsConfig.IGNIVORUS_EXCLUDED_BIOMES);

          // ... other dragons (5 lines each instead of 15)
      }

      private static void add(RegistrySupplier<? extends EntityType<?>> entity,
                             String biomeTagPath,
                             IntSupplier weight,
                             IntSupplier minGroup,
                             IntSupplier maxGroup,
                             ConfigHelper.ListValue additionalBiomes,
                             ConfigHelper.ListValue excludedBiomes) {
          ENTRIES.add(new DragonSpawnEntry(
              entity,
              TagKey.create(Registries.BIOME, SaintsDragonsCommon.rl(biomeTagPath)),
              weight,
              minGroup,
              maxGroup,
              additionalBiomes,
              excludedBiomes
          ));
      }

      public static List<DragonSpawnEntry> getAll() {
          return Collections.unmodifiableList(ENTRIES);
      }

      public record DragonSpawnEntry(
          RegistrySupplier<? extends EntityType<?>> entityType,
          TagKey<Biome> biomeTag,
          IntSupplier weight,
          IntSupplier minGroupSize,
          IntSupplier maxGroupSize,
          ConfigHelper.ListValue additionalBiomes,
          ConfigHelper.ListValue excludedBiomes
      ) {}
  }

  ---
  🎯 Decision Framework

  ✅ Centralize:

  1. Dragon-EntityType mapping - Which entity goes where
  2. Biome tag references - No duplication across platforms
  3. Config binding - Link dragon to config values in one place
  4. Spawn entry list - Single source of truth

  ❌ Keep Platform-Specific:

  1. API calls - BiomeModifications vs BiomeModifier
  2. Helper methods - normalizeBiomeId, etc. (or extract to common util)
  3. Egg worldgen - Dragon-specific features (could centralize later)

  ---
  🚀 Benefits

  1. DRY Principle: Spawn data defined once
  2. Maintainability: Adding a dragon = 5 lines instead of 20+
  3. Type Safety: DragonSpawnEntry record enforces structure
  4. Platform Independence: Common code doesn't know about Fabric/Forge
  5. Testability: Spawn registry can be unit tested
  6. Future-Proof: NeoForge/Quilt support = copy platform code, registry stays same

  🤔 Alternative: Per-Dragon Providers

  If we want dragons to "own" their spawn config:

  public class Ignivorus {
      public static DragonSpawnEntry getSpawnEntry() {
          return new DragonSpawnEntry(
              ModEntities.IGNIVORUS,
              TagKey.create(Registries.BIOME, SaintsDragonsCommon.rl("has_ignivorus")),
              () -> SaintsDragonsConfig.IGNIVORUS_SPAWN_WEIGHT.get(),
              // ...
          );
      }
  }

  Then registry just collects:
  DragonSpawnRegistry.register(Ignivorus.getSpawnEntry());
  DragonSpawnRegistry.register(Raevyx.getSpawnEntry());

  Pros: Dragons encapsulate their data
  Cons: More boilerplate per dragon

  ---


  Use the Central Registry approach (first option):

  1. Create DragonSpawnRegistry in common
  2. Register all dragons in one place
  3. Platform code iterates the registry
  4. Config values stay as suppliers (dynamic, respects config changes)

  Why?
  - Spawn data is not really dragon behavior (unlike hunger/sleep)
  - Spawn data is cross-cutting (biomes, weights, group sizes)
  - Central location makes balancing easier
  - Platform code becomes trivial

  When to use Per-Dragon Providers?
  - If dragons have complex spawn logic (custom conditions, time of day checks, etc.)
  - If you want dragons to be completely self-contained modules

  For my case, central registry is cleaner because spawning is already data-driven via config.
